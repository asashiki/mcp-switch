# MCP 2026-07-28 research notes

Updated: 2026-08-23

This note records the protocol changes that directly affect MCP Switch. It is
not a general introduction to MCP.

## What changed

The 2026-07-28 revision introduces a new, request-oriented protocol era. A
modern request carries the protocol/client envelope in `_meta`; the old
`initialize` / `initialized` connection handshake and `Mcp-Session-Id` are no
longer the foundation of the HTTP path. Servers may expose `server/discover`,
and clients can negotiate modern support before falling back to the 2025 flow.

HTTP is still JSON-RPC, but the unit of state moved from a negotiated session
to a self-describing request. This is why the revision can feel like MCP has
"gone back to ordinary HTTP". The useful distinction is not HTTP versus MCP;
it is session-oriented MCP versus request-oriented MCP.

Other changes relevant to a gateway:

- `MCP-Protocol-Version`, `Mcp-Method`, and (where applicable) `Mcp-Name`
  headers make requests easier for HTTP infrastructure to route and observe.
- List/read responses can carry `ttlMs` and `cacheScope`, allowing clients to
  cache discovery results without inventing their own lifetime rules.
- `subscriptions/listen` supplies the long-lived channel for change events.
- Server-to-client requests are replaced in the modern era by multi-round-trip
  `input_required` results. A proxy must preserve these results rather than
  flattening them into text.
- Apps and Tasks are formal extensions rather than ad-hoc conventions.

## MCP Apps and ChatGPT

The MCP Apps extension became stable on 2026-01-26. A tool can associate itself
with a UI resource through `_meta.ui.resourceUri`. The UI communicates with its
host over the `ui/*` JSON-RPC bridge; `window.openai` remains a host-specific
compatibility/progressive-enhancement surface.

For MCP Switch this means UI support must remain metadata-preserving and
tool-first. A proxied tool still needs to be usable by clients that do not
render its UI. Resource URIs also need collision-safe gateway namespacing when
two upstream servers publish the same URI.

## Authorization direction

The authorization specification continues to treat an MCP server as an OAuth
resource server. Protected Resource Metadata and RFC 8707 resource indicators
matter for preventing a token minted for one resource from being replayed at
another. Authorization-server issuer validation and the RFC 9207 `iss`
parameter protect the authorization-code callback from mix-up attacks.

Dynamic Client Registration is no longer a safe assumption for every client
and authorization server. Client ID Metadata Documents are the direction to
plan around, while retaining DCR only as a bounded compatibility path where it
is actually supported.
